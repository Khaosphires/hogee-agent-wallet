## 1. An oracle-key confirm sent outside the worker closes a payment SETTLED with no payout, and nothing halts

- **Fingerprint:** `apps/worker/src/jobs/settle-decide.ts:decideSettlement:onchain-confirmed-without-rail-payout-closes-settled`
- **Verifier:** `v-1` (independent, source-only)

### Claimed root cause

settle-decide.ts:105 treats any on-chain CONFIRMED settlement state read at finalized as proof that the worker's own payout happened. It never checks the rail history or the worker's own settle-confirm, so an oracle attestation sent outside the worker closes the row SETTLED with no payout. The worker also treats outside use of its hot oracle key as alert-only, and as nothing at all before the key's first allocator use.

### Description

The worker process loads the hot ORACLE key in the same environment as the agent, lender and relayer keys (apps/worker/src/config/keys.ts:81). Treasury opens a settlement record in state NONE at every Spent (TreasuryState.sol:304). confirmSettlement accepts any payoutRefHash, and its only checks are msg.sender == oracle and state NONE (Treasury.sol:246-248, 433-436). Suppose someone holds the oracle key outside the backend, for example from a copied worker environment, and calls confirmSettlement(spendId, anyHash) soon after the worker's spend is mined. The attack works when that confirm is at or below `finalized` by the first settle-spend pass that sees the payment FINALIZED. On an epoch-finality chain, a confirm in the same epoch as the Spent finalizes together with it. Reconcile and settle-spend both run every minute by default (env.ts:71-72). gather then reads Treasury.settlementState at `finalized` as CONFIRMED (settle.ts:111). decideSettlement returns close SETTLED as its first rule (settle-decide.ts:105), before it looks at the rail history, the binding or the worker's own settle-confirm action. execute writes state SETTLED (settle.ts:199), and close is allowed even while halted (settle.ts:252). No payout is requested, no trace is written and no halt is raised. Result: the payee is never paid. The line's spentMinor, the binding's paidMinor and the invoice stay consumed: only failSettlement returns them (Treasury.sol:263), and the settlement can no longer be failed (Treasury.sol:436). Both the chain (SettlementConfirmed) and the DB (SETTLED) report a payout that never happened. If the confirm finalizes only after the worker's first pass, the payout was already requested. A payout that succeeded makes the later close benign. One still PENDING at close is never polled again, because loadRows reads only FINALIZED and SETTLEMENT_REQUESTED rows. Detection is at most one EXTERNAL_KEY_USE warn log per use (halt-rules.ts:109, reconcile.ts:179). There is none at all while the oracle key has no nonces row yet: inspectNonces reports externalUse only when dbNext is not null (nonces.ts:169), and the allocator later seeds the row from the chain's pending count, absorbing the outside nonce (nonces.ts:67). The FAILED branch is guarded: a FAILED state whose payout succeeded halts with SETTLEMENT_CONTRADICTION (settle-decide.ts:106). No rule covers CONFIRMED without a succeeded payout. The documented alert-only rationale for the oracle key (halt-rules.ts:14-18: a use that moved money is caught by the orphan watch) does not reach attestations. The orphan watch judges only Spent, OwnerSpent and MilestoneFunded (orphans.ts:33), and nothing in the worker watches SettlementConfirmed. Out of scope for this record: an outside failSettlement before a payout is the designed oracle veto (the row closes SETTLEMENT_FAILED and the amount returns to the pocket), and one after a payout halts as a contradiction. An outside SalesOracle.recordSale that inflates the on-chain revenue read by the StageRelease re-check (relay-calls.ts:227-232) has a different sink and root cause and needs its own record. Fix direction: in decideSettlement, close a CONFIRMED settlement to SETTLED only when the rail history for the chain-derived idempotency keys has a SUCCEEDED attempt. Preferably also require the SettlementConfirmed log's payoutRefHash to equal keccak256Utf8(payoutId) of that attempt. Otherwise return blocked('SETTLEMENT_CONTRADICTION'), which halts with an ALERT trace (settle.ts:179-191). gather must then fetch that history for a CONFIRMED row even when the binding no longer reads OK, or a legitimately confirmed row whose payee re-bound would halt. Separately, seed a nonces row for every worker key at start-up, and record outside oracle and lender use as a persisted halt event, not a log line. Regression: decideSettlement(facts({ chainState: 'CONFIRMED' })) must return { kind: 'blocked', reason: 'SETTLEMENT_CONTRADICTION' }.

### Source trace

1. **entrypoint** `contracts/src/Treasury.sol:246` — `Treasury.confirmSettlement`: An outside holder of the worker's ORACLE key calls confirmSettlement(spendId, anyHash) for the settlement opened at the worker's Spent (TreasuryState.sol:304). _openSettlement (lines 433-436) checks only msg.sender == oracle and state NONE. The state becomes CONFIRMED with an arbitrary payoutRefHash.
2. **propagation** `apps/worker/src/jobs/settle.ts:111` — `gather`: On the first settle-spend pass over the FINALIZED row, Treasury.settlementState(settlementId) is read at the finalized block and maps to 'CONFIRMED' (CHAIN_STATE, line 129).
3. **propagation** `apps/worker/src/jobs/settle-decide.ts:105` — `decideSettlement`: The first rule returns { kind: 'close', to: 'SETTLED' } for CONFIRMED. The empty rail history, the binding verdict and the missing settle-confirm action are never consulted. Contrast line 106, which halts on FAILED plus a succeeded payout.
4. **propagation** `packages/chain/src/nonces.ts:169` — `inspectNonces`: [second path] Detection of the outside oracle transaction: externalUse is true only when a nonces row exists (dbNext !== null). Before the worker's first oracle transaction there is none, and allocateFromStore (line 67) later seeds the row from the chain's pending count, which silently absorbs the outside nonce.
5. **propagation** `apps/worker/src/jobs/halt-rules.ts:109` — `judgeNoncePass`: [second path] When the oracle does have a nonces row, outside use yields only an EXTERNAL_KEY_USE alert, not a halt. reconcileNonce raises next_nonce (nonces.ts:277), and reconcile.ts:179 writes a single warn log.
6. **sink** `apps/worker/src/jobs/settle.ts:199` — `execute (case 'close')`: The payments row moves to SETTLED, with no payout, no trace and no halt. The halt gate at line 252 exempts close, so this also runs while the worker is halted. Afterwards loadRows no longer selects the row, so no payout is ever requested or polled.

## 2. A copied founder-signed OwnerSpend or MilestoneRelease opens a settlement the worker never pays or fails

- **Fingerprint:** `apps/worker/src/jobs/settle.ts:loadRows:third-party-executed-founder-signed-settlement-never-adopted`
- **Verifier:** `v-2` (independent, source-only)

### Claimed root cause

Settlement starts only from the worker's own successful tx for every kind except WITHDRAW_RESERVE. The contracts let any party submit founder-signed ownerSpend and releaseMilestone calls. When someone else lands the call first, the relayer's row ends REVERTED (or POLICY_DENIED), the open on-chain settlement has no row to settle from, and nothing adopts it from the chain.

### Description

The worker relays founder-signed Treasury.ownerSpend and MilestoneEscrow.releaseMilestone calls with the relayer key (agent-actions-founder.ts:143). Neither contract function checks who submits the call. Treasury.ownerSpend (Treasury.sol:325) passes any caller to TreasuryGovernance.ownerSpend by delegatecall. Its onlyDelegated guard only checks address(this) != _SELF (TreasuryGovernance.sol:204-206), and the founder signature covers only the struct and the domain (line 55). releaseMilestone refuses only the agent as sender (MilestoneEscrow.sol:94).

Attack: a party that can see the relayer's pending tx (a public Sepolia mempool, or anyone with access to the node's pool) resubmits the identical calldata from its own EOA with a higher priority fee. The copy is mined first. It uses up the founder's envelope nonce (TreasuryGovernance.sol:54), marks the invoice paid, adds the amount to the line's spentMinor and the payee's paidMinor, and opens settlement spendId (TreasuryState.sol:297-310). OwnerSpent is emitted in the copy's tx. For a milestone, escrowRelease adds the amount to paidMinor and opens the milestone settlement (TreasuryModuleHooks.sol:57-66), with MilestoneReleased in the copy's tx. The relayer's tx was already signed, so it is mined next and reverts InvalidSignature because the nonce is used (HogeeDomain.sol:67). Recovery records it as INCLUDED from its own receipt (recovery.ts:161), and finality marks the payments row REVERTED (finality.ts:130). A second path: if the same signed struct runs before the relayer signs (for example, submitted outside Hogee), the relay simulation refuses it. The row then becomes POLICY_DENIED with an ALERT trace that reports a signature refusal (agent-actions-founder.ts:122, 151-161).

Why nothing recovers it: settle-spend only loads FINALIZED or SETTLEMENT_REQUESTED rows that have a tx_hash (settle.ts:71-72). The bindings only read the logs of row.tx_hash (settle-verify.ts:37, settle-verify-escrow.ts:68). The worker adopts a third-party execution only for WITHDRAW_RESERVE (settle-adopt.ts:82, called at settle.ts:246), even though that module gives the same reason itself: anyone may execute, so the tx may not be the worker's (settle-adopt.ts:4-5). On the mempool-copy path nothing raises an alert. The orphan watch returns early for an OwnerSpent whenever any OWNER_SPEND row has that intent, including a REVERTED one (orphans.ts:147). It never judges MilestoneReleased (orphans.ts:117). A reverted finality outcome raises neither a halt nor an alert (halt-rules.ts:73-76).

Result: the settlement stays open (isIntentUsed is true and settlementState is NONE). Only the oracle can close it (Treasury.sol:433-437), and the only worker code that calls confirmSettlement or failSettlement needs a loaded row (settle.ts:214, 220). The rail never pays the payee or supplier. Meanwhile the line pocket's spentMinor (or escrowedMinor) and the payee's paidMinor stay used up, so the budget stays locked until someone uses the oracle key by hand. The founder cannot retry the same invoice: the same amount reverts DuplicateIntent (TreasuryGovernance.sol:64) and another amount reverts DuplicateInvoice (TreasuryState.sol:281). The founder cannot retry the same milestone either (MilestoneLocked, MilestoneEscrow.sol:100). Each retry with a new invoice can be copied again for the cost of gas.

Conditions: an anonymous chain user with gas. That user must be able to see the relayer's pending tx before it is mined: possible on a public network such as Sepolia; the localhost Anvil demo exposes its pool only to local processes, and automine leaves no gap to exploit. The founder must sign an OwnerSpend or MilestoneRelease through Hogee. No value is redirected. The impact is a lasting denial of an authorised payment, with its budget and the payee's lifetime cap locked.

Fix: extend settle-adopt.ts to OWNER_SPEND and RELEASE_MILESTONE. For each backend row of those kinds that ended REVERTED or POLICY_DENIED (or is still DROPPED or unresolved), check at finalized whether its intent is used: isIntentUsed of the spendId or the milestone settlement id. If it is, read the finalized OwnerSpent or MilestoneReleased log for that id and insert a worker-owned row under its own id prefix, with that tx hash and its rebuilt signed bytes, as adoptReserveWithdrawals does. The existing binding (settle-verify*.ts) and the rail flow then pay it exactly once. Also alert on an OwnerSpent or MilestoneReleased whose only rows are REVERTED or POLICY_DENIED. Regression test: a fixture where a foreign EOA executes the founder-signed call first; settle must pay exactly once and confirmSettlement must land.

### Source trace

A third-party EOA submits calldata copied from the relayer's pending tx: the founder's OwnerSpend plus its Sig.

## 3. Body size caps trust Content-Length, so a chunked request body is buffered in full before any limit applies

- **Fingerprint:** `packages/api/src/http/register.ts:readBody:size-cap-trusts-content-length`
- **Verifier:** `v-3` (independent, source-only)

### Claimed root cause

tooLarge() trusts the client's Content-Length header, and an absent header counts as 0. readBody then fully buffers the body through c.req.parseBody() or c.req.text() with no streamed byte limit, so the declared caps never bound a chunked body.

### Description

register.ts declares MAX_JSON_BYTES (256 KiB) and MAX_UPLOAD_BYTES (10 MiB) and says JSON bodies above the cap are refused before parsing. The only check made before the read is tooLarge(), and tooLarge() reads only the Content-Length header. A request sent with Transfer-Encoding: chunked has no Content-Length, which counts as 0, so the check passes. For multipart routes, readBody then calls c.req.parseBody(), which reads the whole body through Request.formData(). For JSON and raw routes it calls c.req.text() and compares text.length only after the full body is in memory. uploadInspection copies the file again with file.arrayBuffer() and runs a JS keccak256 over every byte. Its only checks are size 0 and the client-declared part type, and both come before any database or escrow lookup, so no escrow order needs to exist. Reaching these paths takes no credential. The persona gate passes requests without a cookie because they read as founder:rina, which satisfies uploadInspection's FOUNDER list. The Stripe webhook has no persona list, and its header schema needs only a non-empty stripe-signature, because the HMAC is checked in the handler after the full read. Other JSON routes with no persona list (exception approve and veto, control pause) reach the same text() read. No front layer limits size. rejectUntrustedRequest checks only Host and Origin/Sec-Fetch-Site, there is no proxy.ts or middleware, next.config.ts sets only headers, and createApiApp adds no body-limit middleware. The Host allow-list (default localhost:3000 and 127.0.0.1:3000), the Origin guard and the start script's loopback bind mean the attacker is a local non-browser client, unless the deployment exposes the port another way. Such a client can make the shared Next/API process hold request bodies of any size it chooses, held only while each request lasts. Memory grows with the size of concurrent bodies, up to about twice the body on the upload path, plus hashing CPU. Enough concurrent large bodies could exhaust process memory. That would stop the founder and officer UI and Stripe webhook intake until a restart. The worker, its keys and on-chain state are not affected. Whether Next.js 16.4 or undici adds a byte limit could not be checked: no dependency source is installed, and execution is forbidden in this run. ## 4. A veto marks a loosening CANCELLED before cancelLoosen lands. A cancel that runs before the in-flight queueLoosen is refused for good and never reconciled, so the vetoed loosening can still be queued and executed

- **Fingerprint:** `packages/api/src/routes/exceptions.ts:veto:cancelled-before-onchain-cancel-never-reconciled`
- **Verifier:** `v-4` (independent, source-only)

### Claimed root cause

The veto commits a terminal CANCELLED status that is not bound to the on-chain cancellation. CANCELLED is written before cancelLoosen is confirmed. The relay maps a simulated TimelockActive revert to a permanent refusal even while the exception's own lender-co-signed queueLoosen is signed but not yet included (and recovery may still re-send it). No job compares CANCELLED exceptions with Treasury.queuedLoosen(loosenId) or with LoosenQueued events. The decision to emit a cancel is also taken from the read before the UPDATE, not from the row the UPDATE moved.

### Description

POST /api/exceptions/:id/veto has no persona list, so any caller can veto a timelocked exception that is FOUNDER_SIGNED, APPROVED, QUEUED or EXECUTABLE. A request with no cookie reads as the founder. In one API transaction veto() sets the terminal status CANCELLED. If the read taken before the UPDATE was not FOUNDER_SIGNED, it also parks an unsigned Treasury.cancelLoosen row. Nothing waits for the chain. An exception stays APPROVED from the officer's approval until sync sees the loosen QUEUED on-chain. A veto at APPROVED can therefore arrive while the lender-co-signed queueLoosen is signed and broadcast but not yet included. The next relay pass runs the cancelLoosen builder, which checks only the DB status and loosen_id. signAndStore then estimates gas at the node's default block. If that state does not contain the queueLoosen, TreasuryGovernance.cancelLoosen reverts TimelockActive. relay send() turns the decoded revert into a permanent refusal: revert_reason is set and the row is never selected again. Only an ALERT trace records it. The queueLoosen can then be included in two ways: the in-flight tx mines, or, after a failed or dropped broadcast, reconcile's recovery re-sends the stored bytes before the 900 s envelope expires, without re-reading the exception. Either way the loosening is QUEUED on-chain while the console shows CANCELLED. syncLoosens and the timelock executor skip CANCELLED rows, and nothing in the worker or API reads LoosenQueued events. A second veto returns 409, so the officer has no API path left to cancel. After executableAt any EOA can call Treasury.executeLoosen, and the change applies within the _checkLoosen bounds (raised cap, added payee, moved pockets, extended expiry, unpause or reserve withdrawal). The founder who requested the loosening is one such caller. Because anonymous callers read as founder, the founder can also send the veto on purpose during the window to suppress the lender's own veto. The owner EOA or the observer can still cancel on-chain, and a pause cancels every queued loosening, but nothing surfaces the divergence to prompt them. Variants with the same root cause: (a) A veto of an EXECUTABLE row while the relayer's executeLoosen is unmined lets the execution land first. The DB stays CANCELLED while the chain says EXECUTED, and for WITHDRAW_RESERVE settle-adopt never adopts the opened settlement. (b) The cancel decision uses the status read at line 109. An officer approval that commits between that read and the UPDATE leaves CANCELLED with no cancelLoosen row. Meanwhile a relay pass that read APPROVED in that interval co-signs and broadcasts queueLoosen. Timing: on Anvil with automine the main window is near zero, because the tx is mined inside sendRawTransaction. On Sepolia it is about one block. The rebroadcast path does not depend on block time. DEMO_MODE is not required.

## 6. proposeSpend pays consecutive pacing slots back to back; only the worker tick enforces the plan's one-slot-per-day pacing

- **Fingerprint:** `packages/api/src/services/spend-proposal.ts:evaluatePacingSpend:no-pacing-period-check`
- **Verifier:** `v-8` (independent, source-only)

### Claimed root cause

Only the autonomous tick's per-day payment id (decide.ts pacingPaymentId) enforces the plan's per-day pacing cadence. The API proposal path and the worker's re-check of API rows apply core evaluateSpend. Its pacing rule checks only slot order against the in-flight projection and has no due-slot or period rule, and Treasury has none either. A direct path therefore skips a gate that the scheduled path applies.

### Description

Requires DEMO_MODE=1. The proposeSpend route is demoOnly and has no persona list, so any caller (including an anonymous one) or the MCP wrapper can POST /api/proposals/spend {lineKey, pacingSlot, reason}. evaluatePacingSpend takes the amount and payee from the manifest. It then runs core evaluateSpend on the context projected past in-flight rows. The API counts POLICY_OK rows as in flight. So once slot N is a POLICY_OK row, slot N+1 equals the projected nextSequence and the verdict is AUTO. Each AUTO verdict inserts a SPEND row with a fresh newId('pay') id. agent-actions signs API rows oldest first. It rebuilds the projection after each signature and re-evaluates with the same rules, so the agent key signs every row. If slot N+1 runs ahead of an unmined slot N on a chain that does not auto-mine, its gas estimate reverts before signing. The row then stays POLICY_OK and a later pass signs it. Neither evaluateSpend nor Treasury._requireInvoice has a time or period rule: Treasury checks only slot == seq + 1 and amount <= pacingMinor. The one-slot-per-line-per-chain-day rule exists only in the autonomous tick (payment id pacing:<LINE>:<day>). Yet the founder-signed manifest fixes pacing.period = 'day', and project.md section 12.4 says a pacing line gets at most one slot per day. The burst stays within every signed money cap: perTx, the 7-day window cap, the line allocation, releasedMinor/fundedMinor and the payee lifetime cap if any. It pays only the plan's payee. With the Rina ADS numbers, 8 slots (60,000 minor, the window cap) can be paid in one chain day instead of over about 8 days, and the 120,000 allocation can be used up in two windows. The effect is spending ahead of the signed schedule, not diverting funds. Pacing refusals are only traced, never recordDenied, so the burst cannot trip the line circuit.
