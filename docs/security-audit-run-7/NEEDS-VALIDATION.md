## 1. Anonymous shortlist, exception and inspection-upload writers grow the trace table without bound, so the whole-history evidence export can be refused for good (run-6 v-1 variant)

- **Fingerprint:** `api:founder-persona-trace-writers-unbounded`
- **Verifier:** `v-1` (independent, source-only)

### Claimed root cause

Unauthenticated founder-persona writers (POST /api/suppliers/shortlist, POST /api/exceptions, POST /api/escrow/:orderId/inspection) append to the export-collected traces table, and to shortlists and exceptions, with no per-facility reuse, count or rate bound. The evidence export still collects the facility's whole trace history under a hard 50,000-row cap. The run-6 v-1 fix bounded only POST /api/signatures/*.

### Description

Any caller without a valid signed cookie is the founder persona (persona.ts:16-18, persona-cookie.ts:64, register.ts:157-158). The request guard admits a non-browser POST that sends neither Origin nor Sec-Fetch-Site from any allowed Host (request-guard.ts:55-62). Three FOUNDER writers that are not demoOnly append to the facility's traces table on every accepted call, with no reuse, count or rate bound. (1) POST /api/suppliers/shortlist needs only a facility row and a valid ShortlistSpec. Every call inserts a new shortlists row and one TOOL_CALL trace, READY or FAILED alike (suppliers.ts:21-47). (2) POST /api/exceptions needs a committed plan. {kind: UNPAUSE, payload: {}, reason: 'x'} passes checkCreate: core has no refusing rule for an UNPAUSE without lineKey (core loosen.ts:111-112), and the API's PolicyContext never sets ctx.loosens, so the 16-live-loosen bound never refuses (policy-context.ts:202-231; core loosen.ts:130, 141). Each call inserts an OPEN exceptions row and one EXCEPTION trace (exceptions.ts:53-60). Only RELEASE_STAGE has a duplicate check (exception-create.ts:38). (3) POST /api/escrow/:orderId/inspection appends one PROPOSAL trace for every successful upload while a milestone waits for evidence, including a re-upload of identical bytes (suppliers.ts:122-145). The evidence export reads the facility's whole trace history and throws EvidenceTooLargeError past MAX_ROWS_PER_TABLE = 50,000 rows (collect.ts:19, 42-45, 145). The cap also counts eval traces, which are filtered out only afterwards (line 146). POST /api/evidence/export answers that error as 409 CONFLICT (routes/evidence.ts:47). Nothing in source prunes traces except the DEMO_MODE Anvil reset, which deletes the whole facility (demo.ts:33-45). On Sepolia, every later export therefore stays refused. Run-6 v-1 accepted this exact impact for the signature writers and bounded only those (request-bounds.ts; G0-DECISIONS.md:342), yet section 12 states that the founder-persona writers are now bounded (G0-DECISIONS.md:336-337). Writer (2) has a secondary effect. listExceptions returns only the newest 200 rows with no paging (services/exceptions.ts:53; schemas.ts:60), and the console requests it with no status filter (apps/web/lib/api/queries.ts:10). About 200 anonymous UNPAUSE requests therefore push a worker-opened RELEASE_STAGE (stage-gate.ts:60) or a server-opened POLICY_ESCALATION (proposals.ts:63) out of the officer's view; the officer can still deny the flood row by row. Reach depends on deployment. By default the only allowed Hosts are localhost:3000 and 127.0.0.1:3000, and browsers' cross-site POSTs are refused, so the attacker is a local non-browser client, or any client of a hosted demo whose HOGEE_ALLOWED_HOSTS names a public host. Smallest fix: apply the run-6 pattern to these writers. Reuse an identical PENDING, READY or FAILED shortlist for the same spec inside a window, or cap shortlists per facility. Skip the trace when an upload's hash is unchanged, and cap uploads per milestone. Dedupe OPEN founder exceptions by kind and payload, cap them per facility, and page listExceptions. As G0-DECISIONS.md:355 already says, the lasting fix is an export that collects a window or an increment instead of the whole history. Regression test: N repeated calls leave the facility's trace count bounded, and exportEvidence still succeeds.

## 2. Red-team runner writes raw case error text, unredacted, into errors/<id>.json and report.json, and its secret scan leaves out the loaded Sepolia RPC URLs

- **Fingerprint:** `redteam/bundle-unredacted-error-text-rpc-url`
- **Verifier:** `v-2` (independent, source-only)

### Claimed root cause

In scripts/redteam/src/run.ts:54-58, the runCase catch builds `${error.name}: ${error.message}` and writes it, with 12 lines of error.stack, to errors/<taskId>.json. It also stores message.slice(0, 300) as the case reason, which b.finish writes to report.json. Both writes go through Bundle.write (evidence.ts:146-151), and none passes through @hogee/chain redactText or shortErrorReason. Raw viem client errors reach this catch from the runner's own reads: sepoliaClock, txFacts, Bundle.receipt, waitForSent, and direct s.client calls in cases. The project documents that these errors carry the request URL (packages/chain/src/errors.ts:2-3). The backstop also misses: secretsOf (safety.ts:36-48) builds the post-write scan list without cfg.rpcUrls, so the scan at run.ts:112 cannot flag a leaked URL.

### Description

On --target sepolia the runner reads SEPOLIA_RPC_URL and SEPOLIA_RPC_URL_FALLBACK into cfg.rpcUrls and builds one viem fallback public client over them. The project treats these URLs as secret because provider API keys live in them. When a case throws, runCase writes `${error.name}: ${error.message}` and 12 stack lines to errors/<taskId>.json as they are, and puts the first 300 characters into the case reason that report.json carries. Nothing on this path redacts. Worker job functions are not the source: they never throw, and they report through shortErrorReason. The runner's own chain reads are the source, and they are raw. The Sepolia clock polls getBlock every 12 s for up to 45 minutes per wait with no try/catch. txFacts, Bundle.receipt, waitForSent and direct s.client calls inside cases are also raw. Suppose both providers fail after the transport's retries and failover, for example on a local network drop, a provider outage or rate limiting on both. Then viem's error reaches the bundle, and packages/chain/src/errors.ts:2-3 says such errors carry the request URL. The post-write scan looks only for role keys, the cookie secret, the officer code, the webhook secret and the memory key, so it finds nothing and the run does not fail. A provider key shared with the worker can therefore sit in a bundle that .gitignore:35 says may be force-added to git as the submission bundle. The same reason is also printed to the operator's stdout (run.ts:62, cli.ts:28). Corrections to the hunter's version: (a) the 'Pull the plug' child is not a vector. runAgentActions never throws (apps/worker/src/jobs/agent-actions.ts:12, 50-53) and the child logs to silentLogger, so plug-child.ts:51 and artifacts/D-plug/crash.json only see config and parse errors, which name no URL. (b) The transport does retry and fail over (clients.ts:148-149), so a 429 from one provider alone does not surface. (c) The database URL and the Xendit key are also missing from the scan list, but no source-visible writer puts them into the bundle; that part is hardening only.

### Source trace

1. **entrypoint** `scripts/redteam/src/config.ts:123` — `loadRunConfig (target sepolia)`: SEPOLIA_RPC_URL (line 123) and SEPOLIA_RPC_URL_FALLBACK (line 124) come from the operator's env and are kept as-is in cfg.rpcUrls (line 133). The header (line 15) notes that these URLs can embed provider keys, which is why config errors name only the variable.
2. **propagation** `scripts/redteam/src/stack.ts:141` — `openInfra`: cfg.rpcUrls become the run's single public client. hogeeTransport (packages/chain/src/clients.ts:147-149) is a plain viem fallback over http(url, { retryCount: 1 }) with retryCount 2 and no wrapper that redacts errors. An error that survives the retries and the failover to the second provider is thrown exactly as viem built it.
3. **propagation** `scripts/redteam/src/clock.ts:71` — `sepoliaClock now / advance / finalize`: now() calls client.getBlock directly. advance() and finalize() poll it (or getBlock('finalized') at line 81) every 12 s (line 62) for up to 45 min (line 63), and until() at line 66 has no try/catch. Other raw reads also reject the case's run(): txFacts (evidence.ts:82), Bundle.receipt (evidence.ts:158), waitForSent (stack.ts:337), and direct s.client calls in cases.
4. **propagation** `scripts/redteam/src/run.ts:54` — `runCase catch`: message = `${error.name}: ${error.message}` with no redactText or shortErrorReason. The worker jobs do redact, for example apps/worker/src/jobs/agent-actions.ts:52.
5. **propagation** `scripts/redteam/src/run.ts:55` — `runCase catch`: b.write(`errors/${c.id}.json`, { message, stack: error.stack split into lines, first 12 kept }). V8's stack starts with the same name: message lines, so the stack repeats any URL line the message holds.
6. **propagation** `scripts/redteam/src/run.ts:58` — `runCase catch`: b.fail stores message.slice(0, 300) as the case reason (evidence.ts:264). The finally block's b.finish (run.ts:108) writes it to report.json (evidence.ts:270). Line 62 also prints it to the operator's stdout.
7. **sink** `scripts/redteam/src/evidence.ts:149` — `Bundle.write`: writeFileSync of the value, JSON-stringified, with no redaction step. errors/<taskId>.json and report.json land in <outDir>/<runId>/ with whatever URL text the error carried.

### Evidence

- `packages/chain/src/errors.ts:2`: The project documents that node and RPC errors can carry a provider URL with an API key, because viem puts the request URL in the message and details. It provides redactText (line 35), shortErrorReason (line 42) and redactError (line 55) for exactly this case.
- `apps/worker/src/runtime/log.ts:23`: Sibling control: the logger turns Errors into shortErrorReason, runs every string through redactText (line 24) and drops url-named fields (lines 20, 30). logs/run.jsonl is therefore redacted, but errors/ and report.json, written by runCase, are not.
- `packages/chain/src/clients.ts:148`: http(url, { timeout, retryCount: 1 }) inside fallback(..., { rank: false, retryCount: 2 }) at line 149. A failure at one provider fails over to the other, so an error reaches the case only after both providers fail.
- `scripts/redteam/src/safety.ts:38`: The scan values are childKeyEnv (with and without 0x), cookieSecret, officerToken, stripeWebhookSecret and the memory key in hex and base64. cfg.rpcUrls is absent. The database URL and the Xendit secret loaded at stack.ts:228 are also absent, but that part is hardening, since no writer of them was found.
- `scripts/redteam/src/run.ts:112`: scanForSecrets(dir, secrets) runs over the whole bundle. With no URL in secrets it returns [], so runSuite does not throw and the bundle is kept.
- `scripts/redteam/README.md:20`: Claimed control: the runner scans every bundle file for the secrets it generated or loaded, and fails the run on a hit. Lines 21-22 list those secrets, and RPC URLs are not among them, which falls short of the 'every loaded secret' boundary.
- `scripts/redteam/test/config.test.ts:49`: The runner's own test treats an RPC URL path as a secret that must never be echoed.
- `apps/worker/src/jobs/agent-actions.ts:50`: This refutes the plug-child path. runAgentActions catches every failure for a facility and returns shortErrorReason(error) (line 52; 'Never throws' at line 12). The plug child uses silentLogger (scripts/redteam/src/plug-child.ts:37). So plug-child.ts:51 and crash.json (ops.ts:47, 70) only see JSON.parse, loadSigners, parseDeployment and config-check errors, and those name no URL.
- `.gitignore:35`: Evidence bundles are ignored except for the final submission bundle, which is meant to be force-added with git add -f. That is the source-visible way a bundle leaves the operator's machine.

### Blockers

- This run allows no target-controlled execution, and the worktree has no node_modules, so viem 2.57.6's error construction can be neither read nor observed. Two facts are unverified. First, whether the error from a failed getBlock, getTransaction or readContract through this fallback transport has 'URL: <rpc url>' in its message and stack, once both providers have failed after retries; the candidates are HttpRequestError, TimeoutError, RpcRequestError, or ContractFunctionExecutionError wrapping one of them. Second, which provider's URL that error names. Only packages/chain/src/errors.ts:2-3 asserts it. This is decisive: if the message does not carry the URL, nothing leaks.
- Whether the operator's SEPOLIA_RPC_URL and SEPOLIA_RPC_URL_FALLBACK carry a provider API key in the path or query is deployment configuration and not visible in source.
- Whether a Sepolia run's bundle that contains an errored case leaves the operator's machine is a process fact. .gitignore:35 intends the final submission bundle to be force-added to git. The runner bundle has no contracts.json or manifest.json, so the API evidence store does not serve it as-is. A clean run writes no errors/ (scripts/redteam/README.md:13), but the report.json reason is written for any failed case.
