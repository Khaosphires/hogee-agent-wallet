# Hardening notes — hogee run-7

Hunter hardening notes kept in ledger bookkeeping (not findings; no verdicts). Grouped by hunter.

**h-g2-auth**

- Live reject does not revoke an open enrolment code (packages/api/src/routes/founder-key.ts:41-61, packages/db/src/founder-enrolment.ts:109-130). If the officer issued a code while a key was pending, that code stays valid for up to 15 minutes after the reject. G0-DECISIONS and the reject trace say a fresh enrolment needs a new code, but that is not true in this state, so whoever holds the outstanding code can re-take the slot as soon as the key is rejected. Fix: in the reject transaction, run `update founder_enrolment_codes set revoked_at = $now where facility_id = $1 and used_at is null and revoked_at is null`, or refuse to issue a code while a key is pending. Regression test: issue code1, register key A, issue code2, reject A, then options(code2) must return 403.
- Rejections are keyed by credential id only (isFounderKeyRejected, packages/db/src/founder-enrolment.ts:133-136; used at passkey.ts:85 and :135). registerFounderKey stores only (qx, qy), so a rejected P-256 key can come back under a new credential id with a fresh code. There is no added capability today, because any code holder could register any key, but the officer's 'never this key again' intent is not enforced. rejected_founder_keys already stores qx and qy; check them in verify and approve as well.
- api-mock parity gap (packages/api-mock/src/founder-enrolment.ts:97-121). The presented code is a single per-store value, not bound to the caller, so any client's next verify after someone's options consumes the code without knowing it; the mark-used step also comes after an await. To match the live API: encode open.id in the mock challenge and require clientDataJSON.challenge to match in verify, and set open.used synchronously before calling the core handler.
- api-mock state machine (packages/api-mock/src/handlers-core.ts:94-123, founder-enrolment.ts:74-80). The mock allows several PENDING keys, and approve neither requires PENDING_LENDER nor refuses when a key is already REGISTERED, so two keys can be REGISTERED and pending() can show the seeded example key after a real approval. If judges should see the live rules: refuse a new credential while a non-rejected pending key exists (contract test line 177 would need a reject first), and make approve answer FounderKeyAlreadySet once any key is REGISTERED.
- api-mock signing (packages/api-mock/src/signing.ts:261-288) accepts any well-formed assertion whatever its credentialId, so the documented G2 rule that a rejected key cannot sign does not hold in mock mode (a documented §26.7 shortcut). Optionally refuse passkey assertions whose credentialId is rejected or not REGISTERED.

**h-g2-data**

- packages/api/src/routes/exceptions.ts:81: the RELEASE_STAGE approval ignores the update's rowCount. A concurrent deny or a duplicate approve still inserts a Treasury.releaseStage action and answers APPROVED. The worker (relay-calls.ts:219-223) and TreasuryGovernance.sol:82 stop any effect, but decide()'s rowCount check should be used here too.
- packages/api/src/services/exception-create.ts:38: the pending RELEASE_STAGE duplicate check is check-then-insert with no lock, so concurrent creates can open two rows for one stage. The on-chain released flag makes this harmless.
- packages/api/src/routes/exceptions.ts:113 with services/signing/founder-payments.ts:36-50: approving a RELEASE_ESCROW_BALANCE requests the MilestoneRelease the server chooses for the order, not the exception's payload idx or evidenceHash. The founder sees the server values in the panel, and finalize marks only the exception that matches, so a mismatched exception stays OPEN.
- packages/api-mock/src/exceptions.ts:127-156, 174-176: the mock's lifecycle differs from the live API. An officer approval before the founder signs is APPROVED (live answers CONFLICT), RELEASE_STAGE executes without a gate check, and only QUEUED/EXECUTABLE can be vetoed. This is an offline demo with no keys, so it only matters for parity.
- Any anonymous POST /api/suppliers/shortlist that produces a new READY shortlist changes the newest shortlistHash, so a founder's SupplierApproval that is already being signed fails at finalize with CONFLICT. This is same-persona by demo design, and today the live checks are stubs, so every shortlist FAILS.

**h-harness**

- scripts/dev-live/src/main.ts:52-53: Postgres is initialised with --auth=trust and superuser 'hogee' on 127.0.0.1:<pg-port>. On a multi-user host, any local OS account can connect as superuser and run COPY ... TO PROGRAM as the developer, and pg_ctl's daemon outlives an unclean launcher exit (SIGKILL skips shutdown). Use scram-sha-256 with a per-run password from a 0600 PGPASSFILE in .data, or listen only on a unix socket inside a 0700 .data directory.
- scripts/dev-live/src/main.ts:95: Anvil starts without --no-cors. Anvil's default allow-origin is '*' (verify for the installed foundry), so any web page the developer visits can send anvil_* / evm_* cheat calls and unlocked-account transactions to 127.0.0.1:<anvil-port>, subject to the browser's local-network-access policy. Keys and funds are dummy, but the local demo's 'on-chain' state can be rewritten. Pass --no-cors.
- scripts/dev-live/README.md:30: Next still loads apps/web/.env* for variables the launcher leaves unset. A REPLAY there switches route.ts to the mock (it then fails loudly at seeding), and MODEL_PROVIDER/provider keys, STRIPE_SECRET_KEY or PRESIDIO_ANALYZER_URL from a developer's file reach the 'no real key, no paid model API' live stack. Set REPLAY and those variables to empty strings explicitly in the web child's env, or refuse to start while apps/web/.env* exists.
- apps/web/app/api/[...route]/route.ts:18-26: REPLAY silently wins over an explicit MOCK_API=0. Throwing when REPLAY is set together with MOCK_API=0 would match the file's 'fail loudly on anything ambiguous' rule. The fallback is to mock, never to live, so this is not a finding.
- packages/api-mock/src/handlers-core.ts:48-56: the mock's setPersona has no officer-token attempt limiter (live: AttemptLimiter, 5 per 15 min). With the shared strong-secret rule this is not brute-forceable, but a shared apps/web/.env.local (same PERSONA_COOKIE_SECRET and OFFICER_TOKEN for MOCK_API=1 and 0) makes mock-minted officer cookies valid in live mode on the same host, because localhost cookies ignore the port.
- scripts/redteam/src/stack.ts:126 and 217: on --target sepolia, openInfra migrates the database and newStack upserts hogee_worker.roles before sepoliaPreflight (run.ts:81) checks whether the database is shared with another deployment. Run the facilities check (and the halt check) before migrations and before any write.
- scripts/redteam/src/safety.ts:25: the shared-DB preflight compares deployment_id strings only. A redeployed final-1 (same id, new Treasury) with a reused dedicated database passes, and the old facility row (fac-rina) and its chain_actions are picked up. Sign binding refuses the stale 'to', so nothing is sent off-deployment, but the run mixes deployments. Also compare chain_id and the Treasury address, or require that no facility row exists for the run's facility id.
- scripts/redteam/src/stack.ts:127-131: the anvil target accepts any --database-url / REDTEAM_DATABASE_URL / TEST_DATABASE_URL and clears every active hogee_worker.halts row before any chain check. A mistaken shared database silently loses its worker halts (the worker's safety interlock), and T29 later halts that schema and clears it with ackThrough 'all'. Refuse a database that holds facilities with chain_id other than 31337 before migrating or clearing.
- scripts/redteam/src/run.ts:106-113: the secret scan runs in the same finally block after b.finish/b.write and infra.close. If either throws, no scan runs and the bundle stays on disk unscanned; run the scan in its own try/finally. scanForSecrets is case-sensitive exact match on hex and base64 forms only, and the generated founder backup-wallet key and soft-passkey key are not in the list.
- scripts/redteam/src/cases/ops.ts:123-125: T29's direct wallet send uses estimateFeesPerGas unbounded and ignores REDTEAM_MAX_FEE_GWEI, the cap forcedSend and the worker apply (Sepolia test ETH only).
- scripts/redteam/src/run.ts:55: errors/<id>.json stack lines embed the operator's absolute local paths (home directory and user name) in a bundle meant to be shared; strip them to repo-relative paths.

**h-replan**

- packages/api/src/services/compile.ts:239-249 stillCurrent does not re-run code 14 against the fresh env.current. A draft compiled before a Treasury-only change (TIGHTEN_*, an executed MOVE_POCKETS/RAISE_CAP/EXTEND_EXPIRY/ADD_PAYEE, a new signed binding) can be reused by draftPlan (packages/api/src/routes/plans.ts:35), offered by planApproval.prepare (packages/api/src/services/signing/plan-approval.ts:67-69) or opened as a REPLAN exception (packages/api/src/services/exception-create.ts:45) with the title '(tighten-only replan)'. Only the eth_call simulation (packages/api/src/routes/signatures.ts:256) and PlanReplan refuse it, so this fails closed. Suggested fix: add replanLoosenings(d.manifest, env.current).length === 0 to stillCurrent, with a regression where a pocket cap is lowered after the draft is compiled.
- packages/api/src/services/compile.ts:122-124 reads draft_id (and so currentIntent) through its own committedPlanRow query, not from world.plan, the row policyWorld validated against the chain. If a commit lands between the two reads, the previous version's intent delta is re-applied on top of the new state: the draft is either flagged REPLAN_LOOSENS or tighter than the founder asked. Suggested fix: use world.plan.draft_id and world.plan.plan_id.
- packages/api/src/services/signing/plan-approval.ts:25-41 (lineRows/panel) does not show the per-line payee set or its changes. A replan that drops a payee (a tightening the chain accepts, which then needs a lender ADD_PAYEE to undo for a static platform payee) is signed without the founder seeing it. Suggested fix: add payee-diff rows.
- packages/core/src/policy/governance.ts:127-136 evaluateReplan builds current with committedPlanFromContext only, without the isSignedPayee additions that packages/api/src/services/compile.ts:73-94 adds. It would therefore deny a replan listing a signed-bound but unlisted payee that PlanReplan accepts. This is stricter (fail-closed), but the two TS mirrors of PlanReplan disagree.
- packages/api/src/services/compile.ts:130-131 takes capMinor and reserveFloorBps from the DB facilities row, although the module comment says the facility is used 'as the CHAIN holds it'. On-chain codes 1 and 7 still bound commitPlan, so this fails closed.
