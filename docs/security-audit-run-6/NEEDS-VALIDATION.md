## 1. Unbounded founder-persona writers can push a facility past the evidence export's whole-history row cap, blocking every later export

- **Fingerprint:** `packages/api/src/evidence/collect.ts:capped:whole-history-row-cap`
- **Verifier:** `v-1` (independent, source-only)

### Claimed root cause

The exporter applies MAX_ROWS_PER_TABLE to each table's whole facility history and fails the entire export when any table exceeds it. The signature-request and signature-refusal writers it collects from accept unbounded growth from any client that reads as the founder persona. Nothing prunes, windows or increments the exported history, so once the cap is crossed the failure persists.

### Description

collect() selects each table's entire facility history, with no time, run or increment window, and throws EvidenceTooLargeError once any table has more than 50,000 rows. The traces count includes eval traces, because they are counted before they are excluded. By design the export then fails instead of truncating. Two of the collected tables, traces and signature_requests, grow through routes that any client past the request guard can call. A caller without a valid signed persona cookie reads as founder:rina, the only persona that POST /api/signatures/request and POST /api/signatures/:id/submit require. Each request that passes prepare() inserts a PENDING signature_requests row and a SIGNATURE trace. Each submit with a schema-valid wrong signature, for example 0x followed by 130 zeros or a passkey with another credentialId, appends an ALERT trace and leaves the request PENDING. One request therefore accepts any number of refusals until its 900-second chain-time expiry, and new requests can be created at will. Neither writer has a per-facility, per-request or rate bound. After about 50,000 such calls, every POST /api/evidence/export returns 409 CONFLICT ('traces has more than 50000 rows for this facility') before any run is claimed, and `make evidence` exits 1. Bundles already on disk stay readable, but no later decision can be exported. The cap is a compile-time constant, and no code deletes traces or signature_requests rows. Recovery therefore needs an operator to edit the hash-chained tables or ship a code change. Who can drive this beyond the facility's own founder depends on deployment exposure. The default allowed hosts are localhost:3000 and 127.0.0.1:3000, and the guard refuses cross-site browser POSTs.

### Source trace

1. **entrypoint** `packages/api-contract/src/routes.ts:117` — `routes.requestSignature`: POST /api/signatures/request, and POST /api/signatures/:id/submit at line 122, are gated only by personas: FOUNDER (founder:rina).
2. **propagation** `packages/api/src/http/register.ts:157` — `register`: The persona comes from personaOf. A missing, unsigned or invalid cookie reads as DEFAULT_PERSONA founder:rina (persona-cookie.ts lines 14 and 64), so the FOUNDER check at line 158 admits any client past the request guard. Lines 156-163 apply no rate, volume or per-facility limit.
3. **propagation** `packages/api/src/routes/signatures.ts:78` — `requestSignature`: Each call that passes prepare() inserts a PENDING signature_requests row and, at line 82, a SIGNATURE trace. Nothing bounds pending requests per facility, kind or refId.
4. **propagation** `packages/api/src/routes/signatures.ts:98` — `refuse`: Any schema-valid wrong signature (verifiedSig, lines 128, 133 and 134) appends an ALERT trace in its own committed transaction and leaves the request PENDING. One request therefore accepts unlimited refusals until its chain-time expiry.
5. **propagation** `packages/api/src/evidence/export.ts:226` — `exportEvidence`: Every POST /api/evidence/export, and make evidence (cli.ts line 29), calls prepare(), which runs collect() over the facility's whole history (line 131). An error there releases the lock and is rethrown at line 253 before any run is claimed.
6. **propagation** `packages/api/src/evidence/collect.ts:38` — `capped`: More than 50,000 rows in any table throws EvidenceTooLargeError. traces (line 136, counted before eval traces are excluded at line 137) and signature_requests (line 92) are selected over the whole facility history with no window.
7. **sink** `packages/api/src/routes/evidence.ts:46` — `evidenceRoutes.exportEvidence`: EvidenceTooLargeError becomes 409 CONFLICT. Every later export of the facility fails the same way, and the CLI exits 1 (cli.ts lines 33-36).

### Evidence

- `packages/api/src/evidence/collect.ts:18`: MAX_ROWS_PER_TABLE = 50_000 is a compile-time constant with no environment override, documented as 'A facility above these sizes is not exported'.
- `packages/api/src/evidence/collect.ts:37`: Each table query gets limit 50,001 appended to its full facility-scoped select. There is no time, run or increment window.
- `packages/api/src/evidence/export.ts:8`: The design states that the export fails on any limit instead of truncating evidence. docs/G0-DECISIONS.md line 277 records the same limits.
- `packages/api/src/routes/signatures.ts:11`: Documented behaviour: a failed verification leaves the request PENDING and writes an ALERT trace.
- `packages/api/src/services/signing/verify.ts:28`: verifyEcdsaSignature returns false when v is not 27 or 28. A signature of 0x followed by 130 zeros, which EcdsaSignature (core schemas/primitives.ts line 96) accepts, is therefore refused. A passkey with another credentialId is refused at signatures.ts line 111 without any cryptography.
- `packages/api/src/services/signing/typed.ts:14`: SIGNATURE_TTL_S = 900n: a request stays submittable for 15 minutes of chain time, and new requests can be created at will.
- `packages/api/src/services/traces.ts:24`: appendIn only inserts hash-chained events. No code in packages/ or apps/ deletes traces or signature_requests rows, so recovery needs an operator database edit or a code change to the cap.
- `packages/api/src/request-guard.ts:12`: Reachability limit: the default HOGEE_ALLOWED_HOSTS is localhost:3000,127.0.0.1:3000, and cross-site browser POSTs are refused (lines 59-61). Only direct clients that send an allowed Host can drive the writers.

### Blockers

- Deployment exposure decides who the attacker is. Whether any principal other than the facility's own founder on the local machine can reach /api/signatures/* and /api/evidence/export depends on the deployed HOGEE_ALLOWED_HOSTS value and on the network exposure of the API or the web /api proxy. The source default is localhost:3000 and 127.0.0.1:3000, and the deployed values are not visible in the repository.
- Confirmation needs a bounded local observation: the export refused with 409 after refused submissions against a lowered cap, with a founder key registered on a local chain and a signable refId. This run permits no target-controlled execution, because the macOS host cannot enforce the required sandbox memory, disk and file-size limits.

(2) POST /api/signatures/<requestId>/submit {"ecdsa":{"signature":"0x<130 zeros>"}} until the facility has more than 5 traces. Each call should answer InvalidSignature and add one ALERT row. (3) POST /api/evidence/export twice. Expected: both return 409 CONFLICT with 'traces has more than 5 rows for this facility', there is no evidence_runs row for a new run, and no new evidence/<runId> directory exists. Stop at the first refusal.

### Owner-observed deployment check

These are owner-observed checks, not audit traffic. (1) Read the deployed HOGEE_ALLOWED_HOSTS and check whether the API or the web app's /api proxy is reachable from any client other than the founder's own machine, for example a shared or public demo URL. (2) Run read-only counts: select count(*) from traces where facility_id = '<facility>'; the same count on signature_requests; and the number of INVALID_SIGNATURE ALERT traces per day, to judge headroom against 50,000. Make the exporter export a window or an increment instead of failing on whole-history size, for example everything since the last READY run, or keep refusal-only ALERT traces outside the cap. Regression: after 50,001 refused submissions, POST /api/evidence/export still returns {runId}.

## 2. Evidence export writes a full new bundle for every state change, with no aggregate limit, retention or per-caller rate limit

- **Fingerprint:** `packages/api/src/evidence/export.ts:exportEvidence:unbounded-bundle-retention`
- **Verifier:** `v-2` (independent, source-only)

### Claimed root cause

The exporter bounds each bundle (50,000 rows per table, 5,000 files, 32 MB per file, 128 MB per bundle) and serialises builds with an advisory lock. Nothing bounds the total. There is no cap on retained runs or total evidence bytes, superseded runs are never pruned, and nothing limits how often a caller or interval can start a new run. Idempotency only short-circuits a byte-identical source state, and both ordinary worker activity and anonymous row-appending routes change that state all the time.

### Description

POST /api/evidence/export has no persona list, is not demoOnly and has no rate limit. Its runId is a hash of everything collect() returns, so any row change produces a new runId. Ordinary worker activity is enough to cause this, and an anonymous caller (persona founder:rina) can also force it: POST /api/signatures/request appends a signature_requests row and a SIGNATURE trace, and a refused POST /api/signatures/:id/submit appends an ALERT trace. Every new run does the same work again. It re-reads one receipt per mined tx and one block per distinct block from the RPC, with no cache. It renames a complete copy of the facility's history into evidence/<runId>; one bundle can be up to 128 MB and 5,000 files. Then verifyBundle checks the whole bundle synchronously on the API process's event loop. Nothing in the repository ever removes earlier ev-* runs: sweep() deletes only .export-* temp folders, and every cap applies to a single bundle. The single-flight advisory lock means one build runs at a time and a concurrent call gets 409, so the export rate is limited by how long a build takes. It is not a volume limit. A caller that repeats {optionally change one row; POST export; wait until it is no longer busy} therefore gets three persistent or shared effects. It adds one full history copy to the evidence volume per iteration. It repeats the full receipt and block fetch against the operator's RPC endpoint, which the worker also uses. It raises the cost of every GET /api/evidence/runs, because listRuns reads and schema-parses up to three 4 MB index files for every retained run before it applies the 200-run slice. This depends on deployment. By default the web app binds localhost:3000, and the request guard refuses foreign Host headers and cross-site browser POSTs, so a web page cannot drive the loop. The caller must be a local process or a client of a deployment that exposes /api.

### Source trace

1. **entrypoint** `packages/api-contract/src/routes.ts:226` — `routes.exportEvidence`: POST /api/evidence/export is declared with req {} and has no personas and no demoOnly, so any caller that reaches /api can start an export.
2. **propagation** `packages/api/src/http/register.ts:158` — `register`: The only per-route gates are demoOnly (line 156) and personas (line 158). Neither applies here, and there is no rate, interval or volume limit. The scope is built from server config at line 163.
3. **propagation** `packages/api/src/routes/evidence.ts:42` — `evidenceRoutes.exportEvidence`: The handler calls exportEvidence(deps, scope, { root }) on every request and returns as soon as the run is claimed. The build continues in the background.
4. **propagation** `packages/api/src/evidence/export.ts:136` — `prepare`: The runId is 'ev-' plus a keccak hash of the format, exporter, facility, deployment, chain, pack hash and the whole collected object (payments, chain actions, signature requests, plans, traces, LLM calls, rationales, denials). Any row change produces a new runId.
5. **propagation** `packages/api/src/evidence/export.ts:227` — `exportEvidence`: Only an existing evidence/<runId> with exactly this runId returns early (created:false). Any other state records a PENDING evidence_runs row and starts a full build.
6. **propagation** `packages/api/src/evidence/export.ts:148` — `build`: Each new run calls fetchChainData for every mined tx hash with no cache, then serialises the whole history, every receipt and every block into a files map of up to 128 MB.
7. **sink** `packages/api/src/evidence/export.ts:193` — `publish`: The complete bundle is renamed into evidence/<runId> as a new directory that persists. No code path in packages/api, apps/worker, packages/db or the Makefile deletes, replaces or caps earlier ev-* runs.

### Evidence

- `packages/api/src/evidence/export.ts:29`: MAX_BUNDLE_BYTES = 128 MB is checked at line 175 together with MAX_BUNDLE_FILES and MAX_FILE_BYTES. It limits one bundle only, not the evidence directory or the number of runs.
- `packages/api/src/evidence/export.ts:203`: sweep() removes only real .export-* directories. It is the only cleanup apart from the tmp rm at line 196. Retained ev-* runs are never pruned.
- `packages/api/src/evidence/export.ts:86`: pg_try_advisory_lock makes builds single-flight, and a concurrent call becomes a 409 CONFLICT. This limits throughput to one build at a time. It does not limit the number of builds or how much is retained.
- `packages/api/src/evidence/export.ts:239`: verifyBundle(files), which is synchronous (tools/verify-evidence/src/index.ts line 38), re-verifies the whole bundle in the API process after every new run is published.
- `packages/api/src/evidence/fetch.ts:52`: Every build issues one eth_getTransactionReceipt per mined tx, and one eth_getBlockByNumber per distinct block at line 60. Concurrency is 4 and nothing is cached between runs.

It slices to MAX_LISTED_RUNS (line 19) only at line 105, so the cost of each listing grows with the number of retained runs.

- `packages/api/src/routes/signatures.ts:82`: requestSignature inserts a signature_requests row (lines 77-81) and a SIGNATURE trace in one transaction on every successful call. The route requires FOUNDER, and that is the default persona.

- `packages/api/src/runtime/deps.ts:51`: The evidence directory is HOGEE_EVIDENCE_DIR, or resolve(dataDir, '..', 'evidence') by default, on the deployment's own volume.

A POST that carries neither header is allowed, so any non-browser client that reaches the host can drive it.
- `apps/web/package.json:9`: Calibration: next start (and next dev at line 7) binds --hostname localhost --port 3000. In the default deployment only local processes reach /api. project.md D2 (line 90) says localhost first, and D17 (line 102) adds an always-on host.

### Blockers

- Reachability is a deployment fact that source cannot settle. By default /api binds localhost and the guard refuses cross-site browser POSTs, so the lower-trust caller exists only if the always-on host (D17), or another deployment, exposes /api to untrusted clients through its network binding, a proxy or HOGEE_ALLOWED_HOSTS.
- The size of the effect needs execution, which this run does not allow. Under the single-flight lock the achievable rate is one bundle per build duration. The real per-run bundle size, build duration, RPC call count and GET /api/evidence/runs latency at N retained runs could not be measured, so it is unknown whether the growth matters within an operator's normal review interval.
- Free space and quotas on the volume that holds evidence/, whether Postgres or the worker shares that volume, and the quota and rate limits of the RPC provider shared with the worker are deployment facts outside the repository.

### Bounded local validation

Use an isolated fixture: local Postgres and Anvil only, no external network, MOCK_API=0, a dummy facility with about 5 mined payments, and HOGEE_EVIDENCE_DIR on a small quota-limited temp volume (for example 200 MB). Then: (1) POST /api/evidence/export and poll GET /api/evidence/runs until the run is listed. (2) Insert one dummy trace row directly, or POST /api/signatures/request for a dummy refId. (3) Repeat steps 1 and 2 four times. After each iteration record the number of ev-* directories, the total bytes under the evidence dir, the eth_getTransactionReceipt and eth_getBlockByNumber calls counted on an Anvil RPC proxy, and the build duration. Expected: one new full-history directory per iteration, total bytes growing roughly linearly, receipt calls per iteration equal to the mined-tx count, and listRuns opening the index files of every run. Stop after 5 iterations and delete the temp volume.

### Owner-observed deployment check

Owner-observed only, no audit traffic. The owner should check: the network binding of the Next server and any proxy in front of /api; HOGEE_ALLOWED_HOSTS on the always-on host; free space and quotas on the evidence volume, and whether Postgres or the worker shares it; and the RPC provider's quota and rate limits shared with the worker. Fix options: (a) keep only the newest run per facility, or cap retained runs and bytes and prune the oldest after a successful publish, under the export lock; (b) restrict POST /api/evidence/export to the officer persona, or enforce a minimum interval between new runs (for example, refuse when evidence_runs has a run finished within the last N minutes); (c) in listRuns, take the newest MAX_LISTED_RUNS ids from evidence_runs ordered by finished_at before reading any files. Regression test: N exports with one row changed between each leave at most the configured number of runs and bytes, and listRuns reads at most MAX_LISTED_RUNS runs.

## 3. DB row labels choose which transactions the evidence bundle and verifier see, so relabelling a mined row drops its tx and events from a bundle that still verifies

- **Fingerprint:** `tools/verify-evidence/src/chain.ts:row-labelled-chain-view`
- **Verifier:** `v-3` (independent, source-only)

### Claimed root cause

DB row state chooses the set of transactions that the bundle and the verifier consider. The exporter fetches receipts only for rows labelled mined and never enumerates the deployment's logs (fetch.ts:27-31). checkChain parses and binds a row's signed tx only when its receipt is present (chain.ts:180-199), and it asks for a receipt only when the row's label says mined (chain.ts:200-204). A non-mined label is never proven: there is no consumer tx for CANCELLED and no (signer, nonce) check. Row values are bound to calldata only for SPEND and FUND_MILESTONE (chain.ts:83).

### Description

The exporter reads chain data only for rows the DB labels as mined. minedTxHashes (packages/api/src/evidence/fetch.ts:27-31) keeps a row's tx hash only when its state is in MINED_PAYMENT_STATES or MINED_ACTION_STATES (fetch.ts:11-12). That list is the export's only chain read (export.ts:148), and the deployment's logs are never enumerated. The verifier works the same way. checkChain parses and binds a row's raw signed tx only while it iterates the bundle's receipts (tools/verify-evidence/src/chain.ts:180-199). It reports a missing receipt only when the row's own label is mined (chain.ts:200-204). So a DATABASE_URL holder can relabel a mined row: a payment to CANCELLED, DROPPED or BROADCAST, or a chain action to BROADCAST or PENDING. The exporter then builds a self-consistent bundle without that tx's receipt or events, and verifyBundle returns ok:true (index.ts:58; make verify exits 0, cli.ts:62). The row's tx hash and raw bytes are still exported (collect.ts:47-51), but nothing reads them. Neither ParsedTx.nonce (crypto.ts:118) nor the row's nonce field is ever compared. The SQL constraints do not stop this. payments_cancelled_iff_nonce_consumed and payments_nonce_consumed_by_foreign_tx (0000_initial_schema.sql:404-405) only require a CANCELLED row to name some other hex32. Any value satisfies them, and that column is not exported (payments-view.ts:64-66). Deleting a row outright is just as invisible, because the export enumerates rows only.

What stays consistent after a drop. The replay has no cumulative state for a non-pacing Spent. It ignores Denied and SettlementConfirmed, and checkRationales needs no event per preimage (rationales.ts:59-67). A refusal row whose recordDenied action was relabelled is still emitted, only without txHash (rows.ts:146,155-160), and checkRows checks an anchor only when txHash is set (audit.ts:82). Partial controls do exist: a skipped pacing slot (replay.ts:112), a non-cumulative milestone total (replay.ts:175), a committed plan without PlanCommitted (plans.ts:156), and later spends that need a dropped fund or loosen (outflow and cap checks). So the omission that verifies is a non-pacing spend, or the last pacing spend or milestone funding; an anchored Denied, CircuitTripped or LoosenExecuted that no later event depends on; or an event that replay does not use, such as FacilityOpened.

The project's own tamper model is an attacker who rewrites hashes.json (verify-bundle.test.ts:1-5). Under it, a bundle editor can make the same bundle directly. This root cause is still separate from unanchored receipts: even when every receipt the bundle includes is genuine, the omission is not detected.

Variant (ii): for OWNER_SPEND, RELEASE_MILESTONE and WITHDRAW_RESERVE rows, checkSpendCall returns early (chain.ts:83). The row's kind, line, payee and amount are never compared with its calldata or with the OwnerSpent, MilestoneReleased or ReserveWithdrawn events.

Variant (iii), with an honest DB: a T29 orphan is an agent-key effect that no signed payment row explains (apps/worker/src/jobs/orphans.ts:2-13). No row names its tx, so it is never fetched. checkOrphans (replay.ts:270-279) sees only receipts that some row owns (chain.ts:181-185), so it does not fire on an exporter-built bundle. A VERIFIED bundle can therefore show the safety pause without the orphan spend that caused it.

Impact limit: a relabelled payment row still names its tx hash, and its Sepolia link would show it mined to a reviewer who checks every row by hand. A deleted row or an orphan leaves nothing to check.

Smallest fix:
- The exporter fetches a receipt for every row tx hash whatever its state. For each CANCELLED row it exports nonce_consumed_by_tx_hash and that tx's receipt and raw bytes. It adds eth_getLogs over the deployment contracts from the deployment block to the export block, with the receipts of those txs.
- The verifier parses every row's raw bytes. Each row that names a tx must have its receipt, or (CANCELLED only) a mined tx in the bundle with the same (signer, nonce). Any listed log whose tx no row owns is treated as an orphan. Non-agent payment rows are bound to their OwnerSpent, MilestoneReleased and ReserveWithdrawn events.
- Per-signer nonce-gap reporting is not a valid check here. The nonce allocator is one row per signer key, shared by every facility (packages/db/src/schema/payments.ts:269-270), so a single facility's bundle has legitimate gaps.
- Completeness against a bundle editor also needs the receipt and log anchoring tracked under unanchored-receipt-content.

### Source trace

1. **entrypoint** `packages/api/src/evidence/collect.ts:57` — `payments`: Payment rows are read from Postgres as stored, with their state label, tx hash, nonce and raw signed bytes. A DATABASE_URL holder can set a mined row to CANCELLED, DROPPED or BROADCAST. Chain actions are read the same way at collect.ts:68 and can be set to BROADCAST or PENDING.
2. **propagation** `packages/api/src/evidence/fetch.ts:29` — `minedTxHashes`: Only rows whose state is in MINED_PAYMENT_STATES or MINED_ACTION_STATES (fetch.ts:11-12) contribute a tx hash. This is the export's only chain read (export.ts:148), so the relabelled row's receipt and block are never fetched, and the deployment's logs are never enumerated.
3. **propagation** `packages/api/src/evidence/collect.ts:50` — `signed`: rawSignedTx is still exported because tx_hash is set. payments.json names the tx and carries its bytes, but the bundle has no receipt for it.
4. **propagation** `packages/api/src/evidence/rows.ts:146` — `refusalRows`: [second path] When a recordDenied action is relabelled, its receipt is not fetched. The agent_refusal row is still emitted, without a txHash (rows.ts:155-160), and checkRows checks an anchor only when txHash is set (audit.ts:82).
5. **propagation** `tools/verify-evidence/src/chain.ts:180` — `checkChain`: Raw txs are parsed and bound to rows only while iterating the bundle's receipts (chain.ts:180-199). A row with no receipt is never parsed, and checkStatus's 'is X but has a receipt' check (chain.ts:134) cannot fire.
6. **propagation** `tools/verify-evidence/src/chain.ts:202` — `checkChain`: A missing receipt is a problem only when the row's own label says mined. Payment rows in CANCELLED, DROPPED or BROADCAST and action rows in BROADCAST or PENDING are exempt, and no (signer, nonce) evidence is asked for. ParsedTx.nonce is never read.
7. **propagation** `tools/verify-evidence/src/chain.ts:83` — `checkSpendCall`: [second path] (variant ii) Rows of kind OWNER_SPEND, RELEASE_MILESTONE or WITHDRAW_RESERVE return before any calldata or event comparison. Their kind, line, payee and amount are not bound to the tx.
8. **propagation** `tools/verify-evidence/src/replay.ts:274` — `checkOrphans`: [second path] (variant iii) Orphan detection sees only events from receipts some row owns (chain.ts:181-185). No row names a T29 orphan's tx, so it is never fetched and never judged. On the relabel path, the replay simply runs on fewer events. Only a skipped pacing slot (replay.ts:112), a non-cumulative milestone total (replay.ts:175), and later spends that depend on a dropped fund or loosen can expose the gap.
9. **sink** `tools/verify-evidence/src/index.ts:58` — `verifyBundle`: ok is checks.every(c => c.ok), so verifyBundle returns ok:true and make verify exits 0 (cli.ts:62) for a bundle that leaves out a mined non-pacing spend, an anchored Denied, a LoosenExecuted that no later spend relies on, or a T29 orphan.

### Evidence

- `tools/verify-evidence/src/crypto.ts:118`: ParsedTx.nonce is computed, but no verifier source reads it. The only other nonce in src/ is the exported row field (bundle.ts:131), which is never compared either.
- `packages/core/src/schemas/enums.ts:239`: CANCELLED is a terminal, signed payment state that keeps its tx hash and bytes. DROPPED and BROADCAST also keep a tx hash. Chain actions have BROADCAST and PENDING (enums.ts:214).
- `packages/db/drizzle/0000_initial_schema.sql:404`: A CANCELLED row only has to name some other hex32 in nonce_consumed_by_tx_hash (lines 404-405), and no trigger restricts state transitions. A raw-SQL writer satisfies the check with any value.
- `packages/api/src/services/payments-view.ts:64`: PAYMENT_COLUMNS leaves out nonce_consumed_by_tx_hash, so even an honest CANCELLED row carries no proof of the tx that consumed its nonce.
- `packages/db/src/schema/payments.ts:269`: The nonce allocator is one row per signer key, shared by every facility the key serves. A single facility's bundle therefore has legitimate nonce gaps, and the fix must use (signer, nonce) collision evidence, not gap reporting.
- `apps/worker/src/jobs/orphans.ts:2`: A T29 orphan is an agent-key effect that no signed payment row explains, so the row-driven exporter never fetches its receipt.
- `tools/verify-evidence/src/audit.ts:82`: checkRows requires an anchoring receipt only when a row has a txHash. A refusal row built without the recordDenied receipt passes.

The verifier never decodes the lender-signed registerFounderKey calldata (abi.ts:34 has no such function; PlanRegistry.sol:82). qx and qy are unindexed log data, so swapping them does not even change the bloom. So an editor can swap the passkey key and re-sign with their own key.
