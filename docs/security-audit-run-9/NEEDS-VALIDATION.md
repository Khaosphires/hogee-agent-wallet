## 1. Mock catalog SupplierApproval re-derives and funds the order at submit instead of the signed struct, so a SUPPLIER reallocation in between funds amounts the founder never signed

- **Fingerprint:** `api-mock/signing.ts:applySupplierApproval:catalog-order-not-bound-to-signed-struct`
- **Verifier:** `v-3` (independent, source-only)

### Claimed root cause

### Description

## 2. cfo-guard re-dates all-time sales and payments with one uncached RPC per block on every pass while holding the single worker job lock, and every recorded sale wakes it

- **Fingerprint:** `apps/worker/src/jobs/cfo-guard-inputs.ts:readGuardInputs:all-history-block-times-under-job-lock`
- **Verifier:** `v-5` (independent, source-only)

### Claimed root cause

apps/worker/src/jobs/cfo-guard-inputs.ts dates every all-time record with a separate uncached RPC. minedPayments and recordedSales filter only on block <= B, and blockTimes has no cache or stored timestamp. It runs inside the single global job lock (runtime/app.ts locked('cfo-guard')), where a job that finds the lock busy is skipped, not queued. packages/api/src/services/sales.ts wakes the job after every new sale, and an any-persona DEMO_MODE route can create those sales.

### Description

New in this range (db731b0..04924cd): the cfo-guard queue (cron */10, env.ts:84) and a wake after every newly recorded sale (sales.ts:222). Each pass runs inside withJobLock (app.ts:188-190, 226). For every facility with a committed plan, and only after the halt and fee-cap checks pass, readGuardInputs selects every mined payment (cfo-guard-inputs.ts:82) and every recorded sale with a landed recordSale (104) at block <= B, with no time window. blockTimes (48-56, called at 183) then fetches the timestamp of every distinct block with one client.getBlock each, 8 at a time, with no cache and no stored block time. The transport is a plain viem http per URL with no JSON-RPC batching (clients.ts:144-151). So the time the job lock is held is roughly ceil(N/8) x getBlock latency for N distinct record blocks, and it grows permanently with history. Source-visible controls checked: the 10 s per-request RPC timeout and retries bound each call, not the pass. statement_timeout bounds DB statements only (env.ts:68-71). The 300 s pg-boss expiry does not abort the handler, which ignores the job (boss.ts:29, 40-42). guardActions is capped at 200 rows. The exclusive queue drops a wake only while a cfo-guard job is already queued or active (boss.ts:2-3, 36). Any job that finds the lock busy is skipped, not queued, until its next cron tick (lock.ts:30-32). That covers reconcile (agent-key/nonce check, orphan watch, orphan safety pause), settle-spend (payout confirm/fail) and relay (including the officer's Treasury.pause). Input-to-cost path: with DEMO_MODE=1, POST /api/demo/sale (no persona list, no limiter) creates a Stripe test PaymentIntent. The signed webhook inserts one sale and one SalesOracle.recordSale action, and once relayed and landed that sale is a permanent extra block in every later pass. Each new sale also wakes cfo-guard at webhook time, even before the sale lands. A caller who streams sales can therefore re-start a full pass over the existing history within seconds of each completion. Partly self-limiting: new sales add to N only when record-sale and finality get the lock and the oracle key pays gas, and the record-sale and cfo-guard wakes contend with each other for the lock. The history already built stays, and nothing short of deleting rows recovers it. Possible result (estimated, not measured): N = 2,000 distinct blocks at 150 ms per getBlock holds the lock for about 38 s per pass. With back-to-back passes, the share of reconcile, settle and relay minute ticks that run falls to about gap/(pass + gap). The RPC volume is about N getBlock calls per pass on the endpoint all jobs share, times (144 cron passes plus the wake-started passes) per day. The guard only needs operating spend for the last min(7, sampleDays) days (burn.ts:33-36), the first counted-record day (ledger.ts:117, 145) and whether any revenue exists (tighten.ts:122-123). Suggested fix: store each record's block timestamp when its block is set (or keep a bounded per-chain cache like the API's). Read only rows in the last MA_DAYS+1 chain days, plus a counted min(block) for the first-record day and an EXISTS for revenue. Keep parity with GET /api/cfo (cfo-guard-inputs.ts:4). Debounce the per-sale wake, and give the pass a deadline. Related variant (hardening): GET /api/cfo dates the same all-time records behind a 20,000-entry process cache (services/cfo.ts:273-296). That cache clears itself when full, so more than 20,000 distinct blocks would refetch on every request.

## 3. Where a DEMO_MODE=1 live API is reachable by anyone but the operator, each anonymous POST /api/demo/sale makes the oracle key sign one more recordSale transaction, with no count or per-pass cap, on the nonce sequence that settlement attestations share

- **Fingerprint:** `packages/api/src/routes/demo-sale.ts:demoSale:unbounded-oracle-recordSale-spend`
- **Verifier:** `v-7` (independent, source-only)

### Claimed root cause

packages/api/src/routes/demo-sale.ts lets any caller of a DEMO_MODE=1 live API create Stripe test sales with no count limit. apps/worker/src/jobs/relay.ts then signs every resulting SalesOracle.recordSale row with the oracle key in one pass, with no per-pass cap and no gas reservation. It uses the oracle nonce sequence that apps/worker/src/jobs/settle.ts also uses for confirmSettlement and failSettlement.

### Description

Pre-existing root cause, unchanged in db731b0..04924cd (run-4 recorded it only as a hardening note). POST /api/demo/sale is demoOnly with no persona list, and register.ts applies no limiter, so in a DEMO_MODE=1 live API (MOCK_API=0) every caller, read as the anonymous founder, can create sales. Each call creates and confirms a new Stripe TEST-mode PaymentIntent for this facility, with a fresh idempotency key. The signed webhook dedupes per event and per PaymentIntent only, so each call inserts one sales row and one unsigned SalesOracle.recordSale chain action, then wakes record-sale. The record-sale pass signs every pending oracle row with the oracle key, under the single global job lock, with no per-pass cap and no balance reservation. Each row takes the next Postgres-allocated oracle nonce and is broadcast without waiting for mining. SalesOracle.recordSale has no on-chain count limit. The same oracle signer and nonce sequence sign Treasury.confirmSettlement and failSettlement in settle-spend. The only balance control is a LOW_BALANCE log warning in tick. Source-visible bounds: DEMO_MODE (production answers 404); a STRIPE_SECRET_KEY that must be a test key; MAX_FEE_GWEI, which caps the price of each transaction but not how many there are; and the officer halt, which stops recordSale signing but also stops settlement. Reachability: the Host allow-list (default localhost:3000 and 127.0.0.1:3000) and the same-origin POST guard block DNS rebinding and cross-site browser POSTs. Both documented live topologies bind Next to localhost: dev-live runs on Anvil (gas is free there), and the Sepolia runbook runs DEMO_MODE=1 on CHAIN=sepolia with the default allow-list. In those topologies only processes on the operator's own machine reach the route, so no lower-trust caller exists. The finding stands only if the owner exposes a DEMO_MODE=1 live deployment to others (HOGEE_ALLOWED_HOSTS plus a non-loopback bind or a tunnel). If that happens, attacker cost is one HTTP POST per oracle transaction: linear volume, no amplification. The persistent effects are spent Sepolia test ETH (operator-funded, no monetary value) and, per pass, O(N) RPC work that holds the job lock while settle-spend and reconcile are skipped. Once the oracle cannot pay for gas, a recordSale that is signed but cannot be broadcast holds an oracle nonce. Later confirmSettlement and failSettlement transactions, which carry higher nonces, then wait until the operator refunds the oracle. Payouts are simulated (MOCK_ONLY), so attestations and the return of failed amounts to the pocket are delayed, not lost. On-chain revenue inflation from the same route is a separate root cause and is not claimed here. Suggested fix: a per-process and per-facility daily cap on demoSale (or make it OFFICER-only); a per-pass cap on oracle-signed recordSale rows; and an oracle balance floor below which recordSale is deferred while settle confirm/fail is still signed.
